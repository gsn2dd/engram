# Measuring recall: a policy bench for an aged brain

**Status:** built and run, 2026-08-16. Steps 1 and 2 of the sequencing below are
done and shipped (`path_memory/bench.py`); steps 3 and 4 are not started. What
the first run found is at the end.

## Why now

Every experiment on the [roadmap](../ROADMAP.md) is gated on the same sentence:
*only testable against an aged brain.* That gate is open. mindspace now holds
4,111 memories, 3,495 raw link footprints, 544 topics and months of real daily
use — it is the aged brain the roadmap has been waiting for, and it is sitting
on the same machine as the engine.

The prompt for writing this down was a talk by Stefania Druga (Sakana AI) on
memory harnesses, which did the one thing engram has never done to itself: fix
the model, vary **only the recall policy**, and score the result. Three of her
findings are directly actionable here, and one of them is a flaw in this engine
(see *The retrieved-is-not-used problem* below).

The point of a bench is not tuning. It is that engram's README makes an honest
split between what is *proven* and what is a *bet* — and the bet is precisely
the part that has never had a number attached to it. This is how the bet gets
settled, in either direction.

## What already exists, and why it has been lying

There is already a recall self-test. It lives in
`/home/ec2-user/claude_daily_checkin.py` (host, not in this repo), it wrote 28
rows into a `recall_self_test_log` table, and it ran daily at 08:00. It samples
five random memories, asks Haiku to write a natural query for each, and measures
where the source memory ranks under cosine search.

Two things are wrong with it, and both are instructive.

**1. It has been measuring a vector-space mismatch, not recall.** The corpus was
migrated to `gemini-embedding-001` on 2026-07-14. The self-test still embeds its
probe queries with OpenAI `text-embedding-3-small`. Query vectors from one model
compared against corpus vectors from another are not a weaker signal — they are
*no signal*. The log shows exactly this: 5/5 hit@5 with `avg_rank 1.0` every day
up to and including the 08:00 run on 07-14, then **0/5 on 07-15, 07-16 and
07-17**, straddling the migration precisely.

So the instrument worked. It detected a real, total regression the day it
happened. Nobody read it. Three days later the whole job died on an unrelated
`ANTHROPIC_API_KEY` resolution failure, and the last thing it ever recorded was
a score of zero.

The lesson is not "fix the embedding call". It is that **a diagnostic nobody
reads is not a diagnostic**, and that the bench needs an owner — a threshold
that fires, not a number that accumulates.

**2. It measures the wrong layer.** It issues raw cosine SQL directly against
`memories`, bypassing the engine entirely: no use-history multiplier, no
temporal factor, no supersession, no spreading activation, no collapse, no
tiers. Its own docstring is candid about this ("only detects drift in the
embed/recall pipeline itself... not real-world query coverage").

That is a legitimate thing to measure. It is just not the thing we now need.
They are two different instruments and should stop pretending to be one:

- **The health probe** — is the pipeline sane? Cheap, daily, self-supervised,
  no labels, one threshold that alerts. This is the existing test, fixed and
  moved into the engine.
- **The policy bench** — which recall policy is best? Expensive, on demand,
  needs ground truth. This is the new thing.

## Ground truth without a labelling project

The hard part of any bench is labels. Four sources exist in the corpus today,
ordered by what they cost and how much they flatter us.

**1. Self-retrieval probes — free, weak, already built.** Generate a paraphrased
query from a memory's subject and body; the correct answer is that memory.
4,111 available. This is the health probe. Its weakness is structural: it tests
whether the brain can find a *known target from a paraphrase of itself*, which
is an easier task than answering a question, and it will always score higher
than reality.

**2. Wikilink pairs — free, and the only signal we cannot game.** 221 memories
carry `[[...]]` references to other memories. That is a human-and-agent-authored
*these belong together* graph, and critically it was **not produced by the
ranker**. Every other relevance signal in this corpus (edge weights, access
counts, topics) was generated by the very system under test, so using it as
ground truth is circular. The wikilinks are not. Query with memory A's subject;
the ids A links to should appear. This is the best free source we have and it
should be built first.

**3. Supersession chains — free, small, sharp.** 17 rows carry `superseded_by`.
Ask about the topic; the replacement must outrank the row it replaced. Tiny n,
but it is a precise unit test of one ranking term (`SUPERSEDED_FACTOR = 0.4`)
rather than a fuzzy aggregate.

**4. Transcript-derived question→answer pairs — costly, and the real thing.**
The transcripts are already ingested (1,357 rows at `tier='transcript'`). For a
real question asked in the past, which memory actually *informed* the answer?
This needs labelling — and it is the same signal needed to fix the flaw below,
which is why it is worth paying for once. Target ~60 questions, mirroring the
scale of the talk's n=68.

Sources 2 and 3 need no model calls beyond embedding and can be built in an
afternoon. Source 4 is the investment. Do not wait for it to start.

## The ladder

Fix the model, the corpus snapshot, the question set and `limit`. Vary one thing.

| # | Policy | What it isolates |
|---|--------|------------------|
| 0 | no recall at all | the floor — does memory help on this corpus at all |
| 1 | cosine only — no weight, temporal or supersede terms | the raw embedding |
| 2 | + use-history bonus (`USE_BONUS`) | **does the use-built graph earn its place** |
| 3 | + spreading activation | do use-built edges find what cosine cannot |
| 4 | + collapse | does cutting the tail cost recall, and what does it save |
| 5 | + knowledge-tier filter | does excluding raw transcripts help or hurt |
| 6 | decisions-first ranking | the talk's winning policy |
| 7 | creativity = 0.5 | what serendipity actually costs |
| 8 | oracle — inject the known-correct ids | the ceiling |

Rung 2 is the one that matters most. The entire distinctive claim of this engine
is that use-history makes recall better; rung 1 versus rung 2 is that claim
stated as a measurement, on a corpus old enough for it to mean something.

Rung 6 deserves a note. mindspace has 2,708 `curated` and exactly **one**
`decision` row out of 4,111. The engine has the tier mechanism and does not use
it, while the talk found a ranked decisions ledger beat vector RAG outright. The
bench is how we find out whether that transfers before building it.

**The one code change the bench requires.** `USE_BONUS`, `TEMPORAL_FACTOR` and
`SUPERSEDED_FACTOR` are module constants in `path_memory/recall.py`. A ladder
needs to turn them off without forking the function, so `recall()` should take
an optional `policy` dict that overrides them, defaulting to exactly today's
values. Nothing else changes.

## Three metrics, because they are not the same metric

This is the talk's most transferable lesson, and it is worth being strict about.

1. **Retrieval** — hit@k, MRR, rank of the correct memory. What the existing
   self-test measures.
2. **Answer** — did the agent get the question right, given what recall returned.
3. **Cost** — tokens injected per question, plus model calls.

Report all three per rung, always. A policy that improves retrieval but not the
answer means the bottleneck is downstream of recall and further ranking work is
wasted. A policy that improves the answer while *lowering* cost is the
"bad memory is expensive" result reproducing locally, and it is the strongest
claim engram could make on a Marketplace listing — which is exactly why it must
not be claimed until this bench has produced it.

## The oracle rung is a diagnostic, not a policy

Rung 8 hands the model the provably correct memory. In the talk it still did not
reach maximum score — the model can be given the right memory and ignore it,
misread it, or be confused by it.

Its job here is to split *"we did not find it"* from *"we found it and it did
not help."* The gap between rung 8 and the best real rung is the total headroom
that any recall work could possibly buy. **If that gap is small, stop tuning
recall** — no amount of ranking cleverness will collect it. That single number
should be read before any of the roadmap experiments are started.

## The retrieved-is-not-used problem

The oracle result exposes a flaw in this engine, and the bench is how it gets
confirmed or dismissed.

`path_memory/recall.py:412` says it plainly:

```python
# Being recalled together IS the traversal -- record a footprint between each
# consecutive pair of GENUINE hits.
```

Every recall writes edges between all genuine hits and increments
`access_count` and `weight` on all of them — whether or not a single one
influenced the answer. So the use-built graph is not learning *what proved
useful*. It is learning *what got shown*. Paired with an always-on prompt-time
recall hook, that is a self-confirming loop: what the ranker surfaces gets
strengthened, which makes the ranker surface it again.

That is a specific, plausible mechanism for the drift the roadmap names as the
open question, and it is currently unfalsifiable because nothing measures it.

The fix engram is uniquely placed to build: the transcripts are already
ingested, so the dreaming pass can read an exchange *after the fact*, determine
which recalled ids actually informed the answer, and strengthen on **that**
signal rather than on exposure. Very few memory systems keep the transcript
needed to close that loop. This one already does, for other reasons.

Do not build it before the bench. Build the bench, run rung 1 against rung 2,
and find out whether the graph is helping at all first.

## Where it lives

`path_memory/bench.py` with a `pm bench` CLI, in this repo — not in mindspace.
The established direction of travel is that features proven in mindspace flow
*into* the engine (`mindspace/recall.py` became a thin front-end over
`path_memory` on 2026-08-08); this one should start there.

Ground-truth sets go in `tests/bench/` as JSONL, versioned, so that an outside
user can run the same ladder against their own brain. That matters more than it
sounds: the README asks readers for exactly one thing — *tell us what your brain
remembered and what it forgot* — and currently gives them no instrument to
answer with. A shippable bench turns that request into a contribution someone
can actually make.

`recall_self_test_log` gets promoted into the engine schema at the same time.
The [convergence plan](CONVERGENCE_PLAN.md) deliberately left it behind with the
note *"do not port a table for a feature that does not exist"* — building this
is what makes it exist.

## Sequencing

1. **Resurrect the health probe** (small). Fix the embedding-provider mismatch,
   move it into the engine, give it a threshold that alerts rather than a number
   that accumulates. It is the canary, and it has been dead for a month.
2. **Wikilink + supersession ground truth, retrieval metrics only, rungs 0–5.**
   No model calls beyond embedding, so it is nearly free. This alone answers
   *does the use-built graph earn its place?*
3. **Add answer and cost metrics** on the ~60-question transcript-derived set.
   Unlocks rungs 6–8 and the oracle headroom number.
4. **Only then act** — decisions tier, use-signal strengthening, resolve-then-ridge.

Step 2 is the one that changes what we believe. Steps 3 and 4 are what we do
about it.

## Cost, bounded like everything else here

Nine rungs × 60 questions with an answer call each is ~540 model calls per full
run. Three controls, in the style the dreaming pass already uses:

- **Embed each query once**, not once per rung — query vectors are identical
  across the ladder, and embedding is the only per-rung cost that is pure waste.
- **Retrieval metrics are free.** Rungs scored on rank alone need no answering
  agent; run the answer metric on a fixed subset.
- **A hard call budget** with the partial result reported, so an overrun
  truncates the run instead of the bill.

## What this bench cannot tell us

Stated up front, because the engine's own thresholds already carry this caveat
and it would be careless to drop it here.

- It measures **one corpus, one embedding model, one writing style**. mindspace
  is not a representative brain; it is *our* brain. Anything learned is a strong
  signal for this deployment and a weak one for the general claim.
- **Self-retrieval probes flatter the system**, structurally. Treat rung scores
  built on source 1 as an upper bound, never as a headline.
- **The gold set is authored by the same kind of model being evaluated**, which
  is a known way to measure your own blind spot as though it were performance.
  The wikilink source is the partial defence against this, being the one
  relevance signal the ranker did not generate.
- n≈60 will not separate policies that differ by a few percent. It will
  comfortably separate the ones worth acting on.

## What the first run found (2026-08-16)

The bench was built and run on mindspace: 140 wikilink cases, 272 labelled
pairs, split easy/hard at the median pair-cosine of 0.8462.

**The shipped ranking was worse than plain cosine similarity.** On the held-out
half (n=73, tuned on the other half):

| policy | hit@5 | MRR |
|---|---|---|
| cosine only | 0.479 | 0.308 |
| shipped (`USE_BONUS=0.5`, max-norm) | 0.315 | **0.241** |
| new (`USE_BONUS=0.1`, rank-norm) | 0.493 | **0.344** |

A second, independent ground truth agreed even more starkly. Probing with a
memory's *exact subject line* (n=120) — a question the brain should answer
perfectly — the old ranking returned the right memory first **13.3%** of the
time against cosine's **85.8%**. It was burying exact matches under
globally-popular ones.

**Root cause: the shape of the weight transform, not its coefficient.** Weight
was normalised against the pool *maximum*, and accumulated weight is heavy-
tailed — mean 0.19, max 5.83, only 15% of memories carrying any weight at all.
Dividing by the maximum handed a handful of memories nearly the whole bonus and
promoted them into every result set regardless of the question. That is the same
popularity-beats-relevance defect the bounded multiplier was introduced to fix
in June; it survived because only the coefficient was ever revisited, never the
shape. Rank normalisation is outlier-immune and claims only what the design ever
meant — the *order* of use, not the magnitude.

**The claim, restated as a measurement.** With the fix, use-history now earns
its place: on the hard pairs — the ones cosine cannot find, which is the entire
reason the association graph exists — it is worth **+55% MRR** (0.187 vs 0.121),
while no longer costing anything on the easy ones.

Two findings were recorded and *not* acted on, because the evidence does not yet
support a change:

- **Perspectives cost slightly more than they return** on this ground truth
  (MRR 0.310 vs 0.323 without). The effect is small and within noise at n=140,
  and the probes here are subject lines, whereas the fan-out lenses are built
  for queries phrased as questions — the set may simply not represent what they
  are for. *(Resolved later the same day — see the perspectives section below.)*
- **`temporal`, `supersede` and `level_pick` are all no-ops here**, which is
  expected: the wikilink set contains few calendar-anchored, superseded or
  derived memories. Absence of effect on this set is not evidence against them.

Both are exactly the sort of thing that would previously have been settled by
argument.

## The perspectives verdict (2026-08-16)

The deferred finding above turned out to be worth chasing, and chasing it
properly reversed the first answer twice before settling.

**The claim under test** is engram's first README line: a memory indexed under
several lenses is "findable from angles its literal text would never match". It
is also the most expensive claim in the engine — three lenses meant three model
calls on every `Memory.save()`.

**Three experiments, two ground truths, paired bootstrap throughout.** The
pairing matters: every rung runs identical queries, so comparing per-case
reciprocal ranks is far more sensitive than comparing means, and it is what
exposed the first two results as noise.

| rung | associative, subject probes | associative, question probes | **direct lookup** |
|---|---|---|---|
| no lenses | 0.352 | 0.290 | 0.745 |
| all three | 0.350 | 0.266 | 0.797 |
| questions | **0.366** | 0.260 | **0.799** |
| thematic | 0.347 | 0.278 | 0.750 |
| vantages | 0.353 | **0.301** | 0.747 |

*(MRR. Bold = significant at p<0.05 in that column.)*

**What replicated and what did not.** On the associative task — *given memory A,
find the different memory it links to* — `questions` won with subject-line
probes (p=0.023) and `vantages` won with question-shaped probes (p=0.009), in
opposite directions. Across ten comparisons, one hit each way is what chance
produces. Both were discarded. What survived both runs is that **no lens
configuration beat using none**, and all-three-merged was never better.

The third experiment is the one that mattered, because it tests the lens on its
own design brief: generate a question a memory answers, then look for that
memory. Self-retrieval flatters in absolute terms, which is why the numbers are
0.75+ — but the comparison is paired and one-variable, so the flattery applies
to both sides and cancels. There, `questions` is worth **+0.055 MRR (p=0.015)**
and takes hit@1 from **0.627 to 0.707**. thematic (+0.005, p=0.184) and vantages
(+0.002, p=0.399) changed 4–10 results out of 150.

**The decision.** Generation and retrieval both default to `questions` only.
That is a **3× cut in the cost of a write** with no measured retrieval loss
anywhere — and a small gain, since questions-only (0.7993) edged all-three
(0.7968) even where lenses plainly work.

Why an inert lens is not free: perspective merging takes `max()` of a memory's
literal cosine and its best lens cosine, so a lens can only ever *raise* a
score. An inert lens cannot help the right memory it fails to match, but it can
still promote a wrong one that it happens to match. That asymmetry is why
"harmless if unused" does not hold here.

**The honest caveat, and why the retired lenses are kept in the code.**
`vantages` exists for alias-shaped queries — *what does the production line call
this thing?* — and none of the three experiments probed that. It was retired for
being inert on the queries that were tested, which is not the same as proven
useless. `ENGRAM_LENSES=all` restores the historical three, and existing rows
are never deleted, so reopening the question needs no backfill.

### A methodological note on re-running these

The wikilink ground truth **grows as the brain is used** — writing a memory that
cites `[[an id]]` adds a case. The runs above moved from 140 cases / 272 pairs
to 144 / 282 within a single day's work. Numbers from different days are
therefore not directly comparable, and a rung that "improved" between runs may
simply be facing a different question set. Comparisons must come from rungs run
against each other in the SAME invocation, which is why every table here does
that and why the paired bootstrap is the test used throughout.
